Before you start, check whether this repository documents what to prioritize during
review anywhere (e.g. AGENTS.md, CLAUDE.md, a CONTRIBUTING guide, or similar -- these
are examples, not an exhaustive list of filenames to check). If it does, follow that
instead of the list below. Otherwise, in addition to your own general judgment
(bugs, security, performance, readability, etc.), specifically flag:
- Unneeded backward-compatibility shims -- they add complexity without a real
  compatibility requirement behind them.
- Unneeded fallbacks and unneeded defaults -- both tend to mask problems instead
  of surfacing them, and invite unintended behavior for cases that should either
  be explicit or shouldn't be reachable at all.
- A parameter, field, or return type made optional or nullable when every call
  site is controlled by the same codebase -- don't stop at "does this need a
  default", also ask whether the empty state needs to be reachable at all. If
  every caller, tests included, could supply a real value, the type shouldn't
  admit the empty one either.
- A patch layered onto an existing mechanism where fixing the mechanism itself
  would be substantially better -- a sign the change is preserving the status quo
  out of inertia rather than a real constraint, leaving the code messier over time.
- Complex branching introduced to avoid a small amount of duplication -- when the
  duplicated code would have been simpler to read than the abstraction built to
  avoid it, DRY made the change worse, not better.
- Documentation that hedges or talks around the point instead of stating it
  directly.
- Documentation that depends on context outside itself (e.g. assumes the reader
  shared a conversation, or has tribal knowledge) -- a first-time reader must be
  able to follow it from the doc alone.
